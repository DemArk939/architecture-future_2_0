## Задание 1. Модульная инфраструктура для нескольких сред

### Файлы в модуле [modules/vm/](Task1Advanced/modules/vm/)

- variables.tf — определяет входные параметры модуля. Это «интерфейс» модуля: какие данные он ожидает получить.
- outputs.tf — определяет выходные данные модуля, которые модуль возвращает после создания ресурсов
- main.tf — содержит ресурсы, которые создаёт модуль (диск, ВМ).

### Файлы в окружении [envs/](Task1Advanced/modules/envs/)

Каждое окружение — это корневая конфигурация Terraform, которая использует модуль. У неё своя цель:

variables.tf (окружения) — определяет переменные, которые нужны конкретно этому окружению для работы. Сюда входят:

- учётные данные для провайдера Yandex Cloud (token, cloud_id, folder_id);
- параметры, которые будут переданы в модуль, чтобы их можно было задать через terraform.tfvars;

terraform.tfvars — файл со значениями переменных, определённых в variables.tf окружения.
Здесь задаются конкретные цифры и строки для dev-среды, для stage, для prod.

main.tf (окружения) — содержит:

- Настройку провайдера (Yandex Cloud).
- Вызов модуля vm с передачей ему нужных параметров.

outputs.tf (окружения) — необязательный файл. Если он есть, то определяет, какие значения нужно вывести пользователю
после применения конфигурации. Например, можно вывести IP-адрес созданной ВМ, обратившись к выходным данным модуля.

### Для запуска

- Установленный Terraform.
- Аккаунт в Yandex Cloud с созданным облаком и каталогом.
- OAuth-токен для доступа к API Yandex Cloud.
- SSH-ключ для доступа к виртуальной машине. Если ключа нет, создайте:

```bash
ssh-keygen -t rsa -f ~/.ssh/id_rsa -N ""
```

- Идентификаторы подсетей в каждой зоне для окружений. Их можно получить из консоли Yandex Cloud или через CLI.
- Для каждого окружения (dev, stage, prod) необходимо заполнить файл terraform.tfvars в соответствующем каталоге.
  Определить параметр для подключения yandex_token - OAuth-токен

### Описание файлов CI/CD: plan.yml и apply.yml

В проекте используются два основных workflow GitHub Actions для автоматизации Terraform в окружении dev:

- plan.yml – запускается при создании или обновлении Pull Request (PR) и выполняет terraform plan, публикуя результат в
  комментариях к PR.
- apply.yml – запускается после мержа PR (push в целевую ветку) и выполняет terraform apply для применения изменений.

#### plan.yml Шаги

- checkout – клонирует репозиторий.
- setup-terraform – устанавливает Terraform нужной версии.
- Configure backend – создаёт временный конфигурационный файл для бэкенда, подставляя значения из секретов.
- Terraform Init – инициализирует рабочую директорию с этим бэкендом.
- Terraform Plan – выполняет terraform plan и выводит результат в лог (всё видно в интерфейсе Actions).

#### apply.yml Отличия от plan.yml

- Триггер – push в ветку develop (т.е. после мержа PR).
- Шаг Terraform Apply – использует флаг -auto-approve, что соответствует требованию «apply по кнопке или с флагом
  approval».
- Все остальные шаги идентичны, что гарантирует одинаковое окружение для plan и apply.

## Задание 3. Проектирование целевой архитектуры и оценка рисков внедрения

![Диаграмма](Task3Advanced/Диаграмма%20с4.jpg)

### Описание целевой архитектуры

#### 1. Основные контейнеры

- Клиентские приложения — веб‑ и мобильные интерфейсы для врачей, пациентов, сотрудников и партнёров.
- API Gateway (Kong) — единая точка входа для всех клиентских запросов. Выполняет маршрутизацию, аутентификацию, rate
  limiting и сбор метрик.
- Бизнес-домены (Patient, Appointment, Billing, Inventory, HR, AI) — независимые микросервисы, реализующие
  бизнес‑логику. Каждый домен имеет собственную базу данных (PostgreSQL) и может масштабироваться независимо.
- Identity Provider (Keycloak) — централизованное управление учётными записями и правами доступа (SSO, RBAC/ABAC).
- Платформа данных — централизованный слой для сбора, хранения, обработки и предоставления данных аналитикам. Включает:
    - Kafka — шина событий, через которую общаются все новые домены.
    - Data Lake (S3) — хранилище данных.
    - Kafka Connect S3 Sink — сохраняет все события из Kafka в Data Lake.
    - Apache Flink — потоковая обработка данных.
    - Trino — распределённый SQL‑движок для федеративных запросов к Data Lake, Kafka и DWH.
    - Superset — портал самообслуживания для построения дашбордов и ad‑hoc запросов.
    - Инструменты управления: Apache Ranger (централизованное управление доступом), Amundsen (каталог данных).
- Интеграционный мост (Legacy Bridge) — временный слой для связи с легаси системами (PowerBuilder, старые API, DWH) в
  период миграции.

Все новые домены общаются только через Kafka (публикуют события и подписываются на события других доменов).  
Платформа данных автоматически забирает события из Kafka через Kafka Connect S3 Sink в Data Lake, а Flink выполняет
потоковую обработку.

#### 2. Интеграционный мост (Legacy Bridge): состав и взаимодействие

Интеграционный мост обеспечивает двустороннюю связь между новой событийной платформой и легаси‑системами до их полного
вывода. Он состоит из следующих компонентов:

- Адаптеры Camel (антикоррупционный слой)
    - Приём запросов от легаси‑систем и публикация их в виде событий в топик.
    - Преобразование событий в формат, понятный легаси и отправка ответов.
    - Выполнение минимальных трансформаций и форматно‑логического контроля (ФЛК) для согласования моделей данных.

- Kafka Connect JDBC Source (миграция данных из DWH)
    - Периодически выполняет SQL‑запросы к DWH и публикует результаты.
    - Эти данные через Kafka Connect S3 попадают в Data Lake.
    - Используется для постепенной миграции исторических данных без остановки работы легаси.

- DWH (SQL Server 2008, read‑only)
    - До полного завершения миграции остаётся доступным только для чтения:
        - Легаси‑системы (через Camel) могут читать данные из DWH.
        - Trino может обращаться к DWH для построения отчётов, требующих ещё не перенесённых исторических данных.

- Легаси-системы
    - PowerBuilder — UI для клиник и операторов. Взаимодействует с новой архитектурой только через Camel. Прямой доступ
      к новым базам данных отсутствует.
    - Старые внешние API (SOAP/XML) и файловые обмены (SFTP) также подключаются через Camel.

Таким образом, Camel выступает единым шлюзом для всех легаси‑систем, изолируя их от сложности новой архитектуры и
позволяя постепенно переключать функциональность на новые домены.

### 3. Как архитектура решает задачи компании

| Задача                         | Решение                                                                                                                                                                                                    |
|--------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Портал самообслуживания        | Superset + Trino. Аналитики получают доступ ко всем данным через единый SQL‑движок, без участия ИТ. Доступ контролируется Ranger.                                                                          |
| Интеграция новых направлений   | Новые домены просто начинают публиковать события в Kafka и подписываться на нужные топики. Для чтения данных используют Trino — никаких изменений в центральном DWH.                                       |
| Отказ от легаси                | DWH выводится после миграции всех исторических данных в Data Lake. PowerBuilder заменяется современным веб‑интерфейсом. Camel и Kafka Connect обеспечивают плавный переход без остановки бизнес‑процессов. |
| Near‑real‑time аналитика       | Потоковая обработка в Flink позволяет получать витрины данных с задержкой секунды/минуты. Trino может напрямую запрашивать данные из Kafka для самых свежих событий.                                       |
| Качество и безопасность данных | Ranger управляет доступом; Amundsen обеспечивает каталогизацию и поиск.                                                                                                                                    |

### 3. Обоснование выбора событийного подхода

#### 3.1. Проблемы текущей архитектуры (Camel + DWH)

- Высокая связность: ESB (Camel) выступает «умной шиной», содержащей много бизнес-логики.
  Изменение в одном сервисе часто требует правки шины и DWH.
- Монолитное хранилище: DWH хранит данные всех доменов в одной модели, что замедляет внесение изменений.
- Пакетная обработка: Отчётность строится на батчах, time‑to‑market для новых отчётов измеряется неделями.
- Запаздывание данных: Информация поступает в DWH с задержкой, невозможно строить near‑real‑time аналитику.

#### 3.2. Преимущества событийно-ориентированной архитектуры

| Преимущество                                             | Как достигается                                                                | Выгода                                                  |
|:---------------------------------------------------------|:-------------------------------------------------------------------------------|:--------------------------------------------------------|
| Слабая связность                                         | Домены общаются только через события в Kafka.                                  | Ускорение разработки.                                   |
| Масштабируемость                                         | Каждый домен масштабируется независимо.                                        | Рост числа клиентов и регионов без перепроектирования.  |
| Скорость реакции (near‑real‑time)                        | События обрабатываются потоковыми процессорами.                                | Бизнес получает отчёты с минимальной задержкой.         |
| Гибкость интеграции новых партнёров                      | Партнёр просто подключается к нужным топикам Kafka или публикует свои события. | Новые направления интегрируются быстрее.                |
| Надёжность и восстановление                              | События хранятся в Kafka долго, можно переиграть состояние.                    | Возможность восстановить данные после сбоя.             |
| Поддержка аналитики без нагрузки на операционные системы | Аналитики читают из Data Lake не трогая БД доменов.                            | Не нагрузки на операционные базы из‑за тяжёлых отчётов. |
| Соответствие требованиям Data Mesh                       | Каждый домен владеет своими данными и публикует их через события.              | Устраняется единый владелец.                            |

#### 3.4. Итог

Переход на событийную архитектуру позволяет:

- Быстро масштабировать бизнес;
- Интегрировать партнёров без перепроектирования;
- Получить near‑real‑time аналитику;
- Снизить стоимость поддержки;
- Повысить отказоустойчивость.

### 3. Стратегический роадмап внедрения Data Mesh

#### 3.1. Ключевые роли

| Роль                | Ответственность                                                                       |
|:--------------------|:--------------------------------------------------------------------------------------|
| Data Product Owner  | Владелец данных как продукта                                                          |
| Domain Data Steward | Обеспечивает качество, соответствие стандартам, управляет метаданными внутри домена   |
| Data Engineer       | Строит пайплайны, публикует события, поддерживает инфраструктуру домена               |
| Platform Engineer   | Развивает платформу, предоставляет инструменты доменам                                |
| BI-аналитик         | Потребляет данные из портала, строит отчёты, даёт обратную связь владельцам продуктов |
| Архитектор данных   | Координирует стандарты, схему событий                                                 |

#### 3.2. Этапы внедрения

##### Этап 1: Пилот (0–6 месяцев)

- Выбрать 2 домена-пилота: например, Appointment (запись на приём) и Billing (платежи)
- Назначить роли: Data Product Owner и Data Engineer в каждом домене
- Развернуть платформу: Kafka, Schema Registry, минимальный Data Lake
- Подключить портал: Superset для визуализации потоковых данных
- Обучить команды: Kafka, Trino, основы Data Mesh
- Успех: сокращение времени формирования отчётов по доменам.

##### Этап 2: Масштабирование на критические домены (6–18 месяцев)

- Вовлечь новые домены: Patient, Inventory, HR, AI
- Развить платформу:
    - Внедрить Amundsen (каталог)
    - Запустить Flink для потоковой обработки
    - Настроить Ranger для централизованного доступа (пилот)
- Обучить аналитиков: тренинги по самообслуживанию, переход с Power BI на Superset
- Успех: 80% новых отчётов создаётся бизнесом без участия ИТ

##### Этап 3: Полноценная платформа и отказ от легаси (18–36 месяцев)

- Перевести все домены на событийную модель
- Полностью вывести из эксплуатации:
    - DWH – данные мигрированы в Data Lake
    - PowerBuilder – заменён новым веб-интерфейсом
    - Camel – остаётся только для редких legacy-интеграций, затем отключается
- Запустить новые направления:
    - Подключение фарм-компаний через Kafka
    - Интеграция с производителями электроники
- Успех: TCO снижен на 12%, новые регионы интегрируются за недели, бизнес оперирует near‑real‑time данными
